## Goal

The six Lighthouse pages score performance ≥ 90 (median of 3) on GitHub's runner, so performance can be a hard CI budget again (`WARN_ONLY` and its `TODO(phase-5)` removed).

## What the CI reports show (4 Nov 2026, Chrome 156, 4× CPU)

- Performance 85–91 per page; accessibility, best practices and SEO 100.
- Blocking time ~260–440 ms, mostly React hydration: the react-dom chunk (~73 KB compressed, ~40% unused on `/`) runs a 250–430 ms simulated task at ~3.2 s.
- Simulated LCP ~2.5–3.4 s against FCP ~1.1 s. On localhost the scripts arrive before the first paint, so Lighthouse times the LCP after them.

## Scope

1. Measure first: list the client components on each of the six pages and what each one adds to the bundle and to hydration time (a local production build, Lighthouse with `--view` traces, the bundle analyser output).
2. Cut client JavaScript where the page doesn't need it: server components by default, interactive parts kept small, and anything below the fold or opened on demand loaded on demand. Don't remove features, consent or compliance content.
3. Check that the LCP element (the hero logo on `/`, the lede on list pages) paints without waiting for the scripts.
4. Remove `WARN_ONLY` and update D-049, `qa/README.md` and PLAN.
5. **Header link to /saved** (owner's decision, 4 Nov 2026: header only, option 1). Add a "Saved" link to the header's desktop and mobile menus, after 5.7b is merged, so the `/saved` route exists. It is a plain server-rendered link, so it adds no client JavaScript.
