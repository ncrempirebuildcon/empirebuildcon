## Goal

Visitors can ask about a project, book a site visit or get a gated brochure from the website, with consent recorded exactly as the law and our rules require. The intake API has existed since Phase 4 part 3 (`POST /public/leads`, `/public/site-visits`, `/public/brochure-requests`); this task builds the forms that call it and places them on the project, property and contact pages.

## Scope

1. **One client form component** with three intents:
   - **enquiry:** name, mobile, optional email and message;
   - **site visit:** adds the day (today to 120 days ahead, India time) and the time of day;
   - **brochure:** a gated brochure's link is shown after the lead is saved.
2. **Consent** (AGENTS.md, D-017):
   - two separate checkboxes, never pre-ticked;
   - the required one uses the current lead-form text's label, and its full text can be opened;
   - the optional one uses the marketing text and is sent only when ticked;
   - the text id and version go with the lead;
   - when there is no current lead-form text, the form is not shown, and an honest "enquiries open soon, please call or WhatsApp" note takes its place;
   - a 409 (the text changed) asks the visitor to reload, keeping what they typed.
3. **Phone:** Indian numbers only (the API's rule, D-034). The form says so and points visitors outside India to WhatsApp or email. The API's 422 message is shown at the field.
4. **Attribution:**
   - UTM tags and click IDs (`gclid`, `gbraid`, `wbraid`, `fbclid`, `msclkid`) from the landing address, kept for the browser session (first touch) and sent with the lead;
   - `page_url` is the path only (no query, which may hold personal data);
   - `referrer` is sent only if it is an http(s) address.
   - No cookies and no third-party scripts (Phase 6 owns tracking).
5. **Spam:** the API's honeypot field (`website`) is present, hidden from people and assistive technology, and never filled by the form.
6. **States:**
   - submitting (button busy, no double send);
   - success (thank-you with the reference, and the brochure link for brochure requests);
   - field errors from the API's problem `errors`;
   - 429 "too many tries, wait a few minutes";
   - 503 (not open);
   - offline or network failure.
   - Every message is in a live region.
7. **No JavaScript:** the page says how to call or WhatsApp instead. *(Since 5.7c the switched-off form is shown too, D-049.)* The form needs JavaScript, because it posts through the site's `/api` proxy, which carries the visitor's network for the API's rate limit.
8. **Placement:**
   - project page: enquiry and site visit, plus the brochure form when gated;
   - property page: an enquiry about that home type (`configuration_id`), but none when it is sold out;
   - **`/contact`:** a code route with the contact details from settings (placeholders hidden in production) and the site-visit form with a project choice.
   - The 5.3 links to `/contact?project=…` keep working: the contact page preselects the project.

**Out of scope:** the page-builder `lead_form` block (5.5a reuses this component), OTP, chat, analytics events (Phase 6), non-Indian phone numbers (a later API change).

## Tests required

- **Unit:** the payload builder (consent shapes, marketing only when ticked, path-only `page_url`, referrer filter), UTM/click-id capture (first touch, unknown keys ignored, length caps), the error mapping for 409/422/429/503/network, and the visit date range.
- **Browser:**
  - an enquiry from a project page creates a lead with the consent text version and no marketing consent (checked through the staff API);
  - a site visit from `/contact` with marketing ticked records both;
  - a gated brochure shows its link after the form;
  - mocked 409, 429, 503 and offline answers show their messages, keeping the input;
  - no form and the honest note without a current text (mocked);
  - axe, the enforced CSP and 390 px.
- **Budget:** at most 3 real public submissions per run (the API allows 5 per 10 minutes per network, and `leads.spec.ts` uses 1).
