## Run locally

```bash
# once: PostgreSQL running (docker compose up -d db) and dependencies installed (pnpm install, uv sync)
pnpm --filter @empire/web build      # Playwright starts the built app with `next start`
pnpm e2e                             # from the repo root; starts the API and web app if not running
pnpm --filter @empire/qa lhci        # Lighthouse budgets
```

- `global-setup.ts` runs the database migrations, loads the default amenity catalogue, the SAMPLE projects and the sample leads and visits (`empire-api seed --sample`, idempotent, refused in production) and creates two throwaway accounts (random emails and passwords) with the API's dev/test-only `empire-api create-user`: a super-admin and a sales user. The credentials go to `qa/.auth/` (git-ignored).
- **Sign-in limit:** the API allows 10 sign-in attempts per network per 15 minutes (SECURITY.md §1), successful ones included. A run signs in **six** times (the super-admin and the sales user in the setup project, two in `login.spec.ts`, and two in `account-journeys.spec.ts`: the invited admin after choosing a password, and the same admin with two-factor); every other journey reuses the saved sessions. So locally run the suite once per 15-minute window.
- **Password-reset requests** are limited to 3 per hour per email and 10 per hour per network. A run makes two (`account-journeys.spec.ts`: one for an address with no account, one for the run's invited admin), both to fresh addresses.
- **Email:** the API's development transport keeps messages in `apps/api/.mail-dev/` (git-ignored) and never sends; the journeys read setup and reset links from `GET /api/v1/dev-mail/latest`, as a person would click them in their inbox. The links' tokens are used once and never printed.
- **Two-factor and the `admin_2fa` flag:** the suite never switches the flag on. The database is shared and the specs run in parallel, so every other admin sign-in in the run would be sent to the forced set-up. Two-factor itself is still tested end to end, because an account that turned it on is always asked for a code.
- **Public lead intake** allows 5 submissions per 10 minutes per IP and per phone. A run submits four: one in `leads.spec.ts` (`requestSiteVisit`) and three through the website's forms in `lead-forms.spec.ts`; their error states use mocked answers, and every other lead is added through the staff API. With CI's one retry, one retried submitting test still fits; leave 15 minutes between local full runs (the sign-in limit asks for that anyway). Test leads are named "E2E …" and use random mobile numbers (intake only accepts real-shaped Indian numbers); they stay in the local database and nothing contacts them.
- Journeys create their own cities, localities and projects with a unique run id in the name, so runs never clash on slugs in the shared `empire_dev` database.
- API secrets for the run are generated on the spot unless the environment provides them. You need no real secrets to run the suite.
- **Media** uses the API's fake store (`MEDIA_STORE=fake`, set in `lib/env.ts`): files go to `apps/api/.media-dev/` (git-ignored) and the browser's direct uploads go to the fake store's Cloudinary-shaped endpoint, so nothing reaches Cloudinary and no account is needed. The test files are a few KB each and made in the test.
- On a machine with a pre-installed Chromium, set `PW_CHROMIUM_PATH` to it; otherwise run `pnpm --filter @empire/qa exec playwright install chromium` once.

## Exceptions

- **SEO score:** only a warning until go-live. The whole site sends `noindex` and `robots.txt` disallows crawling until the Phase 9 gate, which Lighthouse marks as an SEO failure on purpose. It becomes an error at go-live (`TODO(phase-9)` in `apps/web/src/app/robots.ts`).
